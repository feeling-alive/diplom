# react-grid-layout: chaotic drag + bottom dead zone + broken resize

**Date:** 2026-05-17 03:48
**Files:** src/pages/Dashboard.tsx, src/pages/Dashboard.test.tsx
**Severity:** high

## Problem

Three user-visible bugs on the dashboard:

1. **Chaotic drop placement** — widgets dropped far from the cursor; positions
   visually mismatched intended cells.
2. **Bottom dead zone** — widgets dragged below a certain Y row simply
   disappeared from view; user could not retrieve them without resetting layout.
3. **Resize did nothing** — pulling resize handles had no effect, or widgets
   resized to wrong sizes.

## Root Cause

Two independent causes compounded into the same symptom set:

**Cause A — Missing `WidthProvider` HOC.**
`<GridLayout>` was used directly without `WidthProvider` and without an
explicit `width` prop. react-grid-layout v2 falls back to an internal default
width (~1200 px) used as the basis for every coordinate calculation:
column boundaries, drag drop targets, and resize math. Since the actual DOM
container was narrower than 1200, the visual cell rectangles and the internal
coordinate grid no longer aligned — every drag and resize was computed
against phantom geometry the user could not see.

**Cause B — Custom client-side pagination of `widgets` by `y`.**
A `paginatedWidgets` memo split widgets into "pages" of 4 rows
(`pageBoundary = 4`). Any widget whose `y >= 4` was reassigned to "page 2"
with `y = y - 4`. With `currentPage` defaulting to 0, dragging a widget below
row 4 caused it to vanish from the visible page. From the user's POV the
widget had disappeared. The reset-layout button was the only escape hatch.

`compactType="vertical"` plus `preventCollision={false}` only made the
disappearance more frequent because the engine was free to push items into
row 4+ whenever a swap freed lower rows.

## Solution

Rewrote `Dashboard.tsx`:

1. **Wrap `GridLayout` with `WidthProvider`** from `react-grid-layout/legacy`
   (in v2 the new typed entry no longer re-exports `WidthProvider` — only the
   `/legacy` subpath does). The HOC measures the parent container with a
   ResizeObserver and injects a correct `width` prop on every render.
2. **Delete pagination entirely.** `paginatedWidgets`, `currentPage`,
   `pageBoundary`, the dots and chevrons — removed. The dashboard is now one
   continuous vertically-scrollable surface inside `main-scroll`. This both
   fixes the dead zone and removes ~50 lines of layout-splitting math.
3. **Adopt the library's own `Layout`/`LayoutItem` types** instead of a local
   `GridItem` shape; removed all `@ts-expect-error` directives that were
   masking the type mismatches the wrong shape had introduced. Callbacks now
   accept the readonly `Layout` and handle `LayoutItem | null` cleanly.
4. **Mock `react-grid-layout/legacy` in the test** (not `react-grid-layout`),
   providing both the default export and a pass-through `WidthProvider`.

`draggableHandle=".widget-drag-handle"`, `resizeHandles=['se','sw','ne','nw','s','e']`,
the iPhone-style placeholderless drag CSS, and per-widget `minW/maxW/minH/maxH`
from `WIDGET_REGISTRY` were preserved from the prior commit.

## Prevention

- **Always wrap `GridLayout` with `WidthProvider`** (or pass a measured
  `width` explicitly). Treat a `GridLayout` without one of those as a bug.
  Document the rule in skill-context.
- **Avoid hand-rolled pagination on top of a virtualised/positioned grid.**
  If pagination is genuinely required, gate it on an explicit user action,
  not on widget `y` coordinates — coordinates change during compaction and
  drag.
- **Prefer the library's published types over local shims.** Whenever an
  `@ts-expect-error` accumulates on every callback, the local type is wrong;
  fix the type, not the suppression.
- **When upgrading react-grid-layout to v2+,** remember that `WidthProvider`,
  `Responsive`, etc. moved out of the main entry. Import from
  `react-grid-layout/legacy` or migrate to the new `useGridLayout` hook API.
